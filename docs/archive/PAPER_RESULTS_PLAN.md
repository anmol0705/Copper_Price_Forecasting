## 2. Ablation study reporting plan

The 4 locked ablation variants (per `vmd-mfgnn-protocol/SKILL.md` §"Locked Ablation Studies"): `full_model`, `no_vmd_raw_price`, `pooled_graph`, `correlation_graph`.

### What to report, per variant, per horizon (from `results/ablation_results.json`)
For each of the 4 variants × 4 horizons: RMSE, MAE, DA (mirroring the main results table's metric set). Read directly from `ablation_results.json[variant][f"h{h}"]` — already aggregated by `compute_metrics()`, same as §1. No computation needed beyond formatting into a table.

Also report, as a one-line capacity caveat specifically for the `pooled_graph` row: `PooledGraphMFGNN` has materially fewer trainable parameters than `VMDMFGNN` at matched `hidden_dim`/`num_heads`/`num_gnn_layers` config — confirmed in `STATUS.md`'s Phase-1 notes at synthetic-data scale (13,450 vs. 59,588 params, a 77% reduction; `pooled_graph_mfgnn.py`'s `count_parameters()` helper is what produces this count). **This count has not been re-verified against the real 2010-2025-scale config** (it may differ slightly since `hidden_dim`/`num_heads` could change if HPO is enabled — HPO tunes `VMDMFGNN` only, so if HPO changes `VMDMFGNN`'s `hidden_dim` the two models' parameter counts will diverge further from whatever ratio was measured at defaults). Before freezing the ablation table, someone should call `count_parameters()` on both actual trained model instances post-Colab-run and drop the real numbers into the paper's ablation discussion, since `pooled_graph`'s accuracy delta is otherwise confounded by capacity, not just graph design — this is explicitly flagged in `STATUS.md` as needing resolution before the novelty-ablation table is frozen.

### CRITICAL: no significance testing is currently possible on ablation comparisons

The evaluation protocol (`vmd-mfgnn-protocol/SKILL.md` §"Data Splits") is a **single chronological train/val/test split**: train 2010–2019, val 2020–2021, test 2022–2025. `run_ablation_studies()` trains each of the 4 variants exactly once, on this one split, with one fixed seed (`set_seed(config["training"]["seed"])`, called once at the top of the function, before all 4 variants — so all 4 variants share the same seed too). There is therefore **no resampling unit** — no folds, no repeated seeds — to compute a variance estimate across. This means: no paired t-test, no Cohen's d, no confidence interval on any RMSE/MAE/DA delta between `full_model` and any other variant is currently computable from what the pipeline produces. The DM test infrastructure that exists (`diebold_mariano_test`) is wired only into `run_significance_tests()`, which compares VMD-MFGNN against the 6 *baselines*, not against the 3 other ablation variants — it is not currently invoked anywhere in the ablation path.

This is a real methodological gap relative to more rigorous papers — e.g. a walk-forward multi-fold protocol (like the CRML paper referenced in `latest-main.tex`) would give a natural resampling unit (folds) for paired significance tests on ablation deltas.

**This is a decision point for the human, not something resolved here.** Three concrete options:

**(a) Ship as-is.** Report raw RMSE/MAE/DA deltas between ablation variants with no significance testing, and add an explicit sentence to the Limitations section disclosing this (e.g. "Ablation comparisons are reported as point estimates from a single chronological train/val/test split; no significance testing across ablation variants was performed, as the single-split protocol provides no resampling unit for computing variance"). Zero extra compute cost — nothing new to run. Risk: a reviewer may flag ablation claims (especially the pooled-vs-per-band claim, which is called out in SKILL.md as "the empirical backbone of the paper's novelty claim") as unsupported by statistical evidence, only by raw deltas.

**(b) Add multi-seed ablation runs.** Train each of the 4 ablation variants with 3-5 different random seeds, all on the SAME single 2010-2019/2020-2021/2022-2025 split (only the model init / data-loader shuffle order changes). This gives mean±std per variant per horizon and lets you compute a paired t-test / Cohen's d across seeds on e.g. `full_model` vs. `pooled_graph`'s per-seed RMSE. This is closer to (but not the same rigor as) walk-forward-fold significance testing, since it captures training-stochasticity variance, not out-of-sample generalization variance across different time periods.
  - **Engineering cost (not yet built, scope only, do not implement):** `run_ablation_studies(config, data)` in `src/trainer.py` (lines 477-559) would need to loop over a list of seeds, calling `set_seed(seed)` before each variant's model construction+fit+evaluate, accumulating results into e.g. `ablation_results[variant][seed] = {...}` instead of the current flat `ablation_results[variant] = {...}`, then a small aggregation pass to compute mean/std per variant/horizon and the paired test. `set_seed()` (utils.py:18-23) already exists and is reusable per-seed. Checkpoint paths (`results/checkpoints/{variant}.pt`) would also need a seed suffix (e.g. `{variant}_seed{seed}.pt`) since the current fixed paths would cause seed 2's run to load seed 1's checkpoint and skip training entirely — a real bug risk if this is built without also fixing checkpoint naming.
  - **Compute cost estimate:** `STATUS.md`'s Phase-1 smoke test measured ablations taking ~105s combined at `epochs=2` (tiny synthetic-scale smoke test). At the real Colab scale, `COLAB_RUNBOOK.md` estimates the 4 ablations combined at **30-90 min total** (`epochs=200`, real 2010-2025 data). Multiplying by 3-5 seeds gives a **rough estimate of 1.5-7.5 hours** added to the ablation stage alone (3×30min=1.5h low end, 5×90min=7.5h high end), on top of the runbook's already-estimated 2-6 hour total pipeline runtime. This is a meaningful fraction of a Colab session and would very likely require multiple additional disconnect/resume cycles. State assumption clearly: this scales the *ablation* stage only, proportionally to seed count, holding everything else in the runbook's estimate table fixed.

**(c) Full walk-forward redesign.** Redesign `create_datasets()`'s single-split logic (`src/data_pipeline.py`) into an expanding-fold generator (multiple chronological train/val/test folds, e.g. rolling 1-year test windows across 2022-2025, or further back), matching the rigor of the CRML paper cited in `latest-main.tex`. Most statistically rigorous option — folds are a natural resampling unit for both the main results table AND the ablation table. But this is a substantial scope change: it touches `data_pipeline.py`'s dataset construction, the VMD expanding-window caching logic (which already refits every 21 days and is keyed to specific split dates per `vmd_modes_meta.json`), every model training call site, and would require re-running the entire pipeline (all 7 models × all folds, all 4 ablations × all folds) from scratch. Given 13 days remain until the 2026-08-20 deadline, this is flagged as **almost certainly not worth it** for this cycle — named here for completeness only.

**Recommendation:** Option (a) for the initial submission, with (b) as a stretch goal only if Colab compute budget and remaining days comfortably allow it after the core run completes and all other Phase 3/4 work is done. Reasoning, calibrated the same way `STATUS.md`'s HPO-asymmetry decision was: this project already made one deliberate rigor-vs-deadline tradeoff (tuning only VMD-MFGNN, not baselines) and disclosed it rather than either skipping HPO entirely or blowing the deadline chasing full symmetry. The same logic applies here — disclosing a real limitation honestly (option a) is standard, defensible practice under a hard deadline, and is much lower-risk than attempting (b) with only ~13 days left and zero real-data results in hand yet. (b) becomes attractive only if the human finds themselves with slack time after Phase 2-3 complete with days to spare; (c) should not be attempted this cycle under any circumstance short of a deadline extension. **This is a recommendation, not a decision — the actual go/no-go on (a) vs. (b) vs. (c) is the human's call.**

## 5. Metrics glossary for the paper

All definitions read directly from `src/utils.py`'s `compute_metrics()` (lines 50-64) and `diebold_mariano_test()` (lines 67-84).

- **RMSE** (Root Mean Squared Error): `sqrt(mean_squared_error(y_true, y_pred))` — standard root-mean-squared prediction error, computed on the (NaN-masked) flattened true/predicted arrays for a given model and horizon.
- **MAE** (Mean Absolute Error): `mean_absolute_error(y_true, y_pred)` — standard mean absolute prediction error, same array basis as RMSE.
- **DA** (Directional Accuracy): `mean(sign(y_true) == sign(y_pred)) * 100`, expressed as a percentage. This measures the fraction of test samples where the predicted and true values agree in sign — i.e., whether the model correctly predicts the *direction* of the target quantity (not its magnitude). Note for the paper's Methodology text: since this uses `np.sign` directly on the model's target values, DA's interpretation depends on what the target actually is (price level vs. price change/return) — confirm against `src/data_pipeline.py`'s target construction before writing the DA definition sentence, so the paper doesn't misdescribe DA as "predicting price direction" if the target is actually something else. (Two metrics present in `compute_metrics()` but not called out in SKILL.md's required reporting — `mape` and `r2` — are available in every results file if a supplementary table is desired, but are not part of the locked scope.)
- **Diebold-Mariano (DM) test**: Tests the null hypothesis H0 that two forecasting models have **equal predictive accuracy** (equal expected squared prediction error), against a two-sided alternative. Computed on the loss differential `d = e1² − e2²` (squared-error difference between the two models' raw errors), using a Newey-West HAC variance estimator with bandwidth `horizon − 1` to account for the serial correlation induced by overlapping multi-step-ahead forecast errors; the test statistic `dm_stat = d̄ / sqrt(var_d)` is compared against a standard normal distribution to obtain a two-sided `p_value`. In the paper's pipeline, `e1` is always VMD-MFGNN's error and `e2` is always the baseline's error (`run_significance_tests()`, trainer.py:439), so a negative `dm_stat` indicates VMD-MFGNN achieved lower squared error than that baseline at that horizon, and a small `p_value` (e.g. below 0.05) indicates that difference is unlikely to be due to chance alone. One-sentence Methodology-suitable phrasing: "We assess whether VMD-MFGNN's forecast accuracy differs significantly from each baseline using the Diebold-Mariano test, which compares the models' squared forecast errors under the null hypothesis of equal predictive accuracy; a Newey-West correction accounts for serial correlation in the multi-step error series."
- **Degenerate case**: `diebold_mariano_test()` returns `{"dm_stat": NaN, "p_value": NaN}` if the estimated variance `var_d <= 0` (a small/near-constant-loss-differential edge case). See §6 pre-flight checklist — this has already been observed at smoke-test scale and must be re-checked at full scale.
